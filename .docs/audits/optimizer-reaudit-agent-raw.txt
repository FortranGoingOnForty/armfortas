## NEW major bugs

### NEW-MAJOR-1 — C-C fix is incomplete: Int width drift inside Select still mis-folds

**File:** `src/opt/const_fold.rs:389-408`

The Select fold now bails when type categories disagree, but it fails to handle width drift WITHIN the integer category:

```rust
(IrType::Int(w), Const::Int(v, _)) => {
    Some(InstKind::ConstInt(norm(v, *w), *w))
}
```

The `_` discards the chosen branch's stored width. If the chosen branch is `Const::Int(255, I8)` (which represents −1 at i8 precision) and `inst.ty` is `Int(I64)`, the result is `norm(255, I64) = 255`, but the correct value is `−1`. The fix should sign-extend at the **source** width first, then renormalize at the destination width:

```rust
let sext_at_src = sext(v, src_w.bits());
Some(InstKind::ConstInt(norm(sext_at_src, *w), *w))
```

This is currently dormant because:
1. `Builder::select` requires both arms to have the same type.
2. The verifier doesn't enforce Select operand-type consistency, but no current pass introduces width drift.

**However**: the audit's stated rationale for C-C was "after IntExtend / FloatTrunc / similar fold chains the chosen operand can carry a narrower width than the Select declares". The chosen operand's stored width is currently captured in the `_` discard. **The fix names the destination width but ignores the source width — half a fix.**

### NEW-MAJOR-2 — Verifier under-strict for Select / FCmp / ICmp / shifts / conversions

**File:** `src/ir/verify.rs:428-486`

`check_type_consistency` only validates IAdd/ISub/IMul/IDiv/IMod (`is_int()`) and FAdd/FSub/FMul/FDiv/FPow (`is_float()`) and Load/Store (`is_ptr()`). The following are NOT checked at all:

- **ICmp / FCmp**: operands may have different widths within the same category.
- **Select**: cond, true_val, false_val types are not validated against each other or against `inst.ty`.
- **Shl / LShr / AShr**: count may be a different width than the value.
- **Conversions** (IntExtend, IntTrunc, FloatExtend, FloatTrunc): operand and dest widths are not validated.
- **And/Or/Not**: are these supposed to require Bool operands? Builder enforces it but verifier doesn't.

This isn't a regression introduced by the fixes, but it's the **root cause** of why so many "latent" bugs in const_fold can sneak past tests. The audit team's rationale for fixes M-D, C-C, Med-3 was "verifier doesn't catch the mismatch". That's still true. **Tightening the verifier is the only way to make these fixes provably watertight.**

### NEW-MEDIUM-2 — DCE outer fixpoint is O(N²) on by_block extraction

**File:** `src/opt/dce.rs:248-265`

`remove_dead_block_params` builds `by_block` and then for each `(target_block, idxs)` pair it iterates `func.blocks.iter_mut()` *twice* per index — once to find the target and once to walk all predecessors. For N blocks with K dead params total, this is O(N · K · 2). The outer DCE loop wraps this in a fixpoint. Worst case O(N² · K). For tiny IR this is invisible; once mem2reg lands and many block params become dead simultaneously, this could become noticeable.

Not a correctness issue. Worth restructuring to a single block-id index map plus a pre-built predecessor map.

### NEW-MEDIUM-3 — `is_hoist_candidate` excludes Load conservatively but Load can also trap

**File:** `src/opt/licm.rs:61-78`

Load is excluded from hoisting "to avoid alias issues". That's correct. But Load can also trap on a null/wild pointer; if we later add memory-aliasing analysis and start hoisting safe Loads, we need to be careful that the hoisted location is provably non-null. Same concern: `GetElementPtr` is **not** excluded — it's pure pointer arithmetic and won't trap on its own. ### NEW-MINOR-3 — `substitute_uses_batch` closure is fragile

**File:** `src/opt/cse.rs:274-288`

```rust
let r = |v: &mut ValueId| { ... };
for block in ... {
    for inst in ... {
        substitute_in_inst(&mut inst.kind, r);
    }
    if let Some(term) = ... {
        substitute_in_terminator(term, r);
    }

```

This compiles because `r` captures `&HashMap<ValueId, ValueId>` by immutable reference, which is `Copy`, so the closure itself is `Copy` and can be passed by value into multiple calls. **If anyone changes the closure to capture mutable state**, the loop fails to compile with a "use of moved value" error. The cleaner pattern is `r: impl Fn(&mut ValueId)` (use `Fn` instead of `FnMut`) **or** call via `&mut r` so each call borrows the closure.

## NEW major bugs

### B-1 — C-C fix is incomplete: width drift within `IrType::Int(_)` is silently misnormed

**File:** `src/opt/const_fold.rs:389-408`

```rust
return match (ty, *k) {
    (IrType::Int(w), Const::Int(v, _)) => {
        Some(InstKind::ConstInt(norm(v, *w), *w))
    }
```

The fix correctly bails on type-category mismatch (Int vs Float vs Bool). But within the Int category, it discards the chosen branch's source width (`_`) and re-norms `v` at the destination width. **`v` is a raw stored value that may not be sign-extended at its source width.**

Adversarial case: `inst.ty = IrType::Int(I64)` and `chosen` is `Const::Int(255, I8)`. The "true" value of the i8 constant is `-1` (sign-extended from 0xFF). The current code computes `norm(255, I64) = 255`, producing `ConstInt(255, I64)` instead of `ConstInt(-1, I64)`.

Required fix: sign-extend at source width first, then norm at dest width:
```rust
(IrType::Int(w), Const::Int(v, src_w)) => {
    let signed = sext(v, src_w.bits());
    Some(InstKind::ConstInt(norm(signed, *w), *w))
}
```

The `Float` arms have the same issue but are saved by the f32-rounding pattern which applies regardless of source width.

**Triggerability today**: low, because `builder.rs::select` derives `inst.ty` from `value_type(true_val)`, which prevents width drift at construction time. But the verifier never enforces it for Select, so any future pass that introduces a width-drifted Select would silently miscompile through this fold.

### B-2 — `strength_reduce` still pays O(M·N) for M Identity rewrites

**File:** `src/opt/strength_reduce.rs:324`

```rust
substitute_uses(func, old_id, pass_through);
```

The Min-1 fix replaced CSE's per-rewrite walks with a batched substitution. **The same problem still exists in strength_reduce**: every Identity rewrite does a full function walk via `util::substitute_uses`. A function with M `*1`/`+0` simplifications takes O(M · function_size).

This is the *same finding as Min-1*, just for a different pass. Min-1's fix is incomplete.

## NEW medium issues

### B-3 — `FCmp` and `FloatToInt` folds still ignore the source operand width tag

**File:** `src/opt/const_fold.rs:173-186, 330-351`

These folds rely entirely on the M-1 invariant (any `Const::Float(_, F32)` value is already rounded to f32 precision). The folds do not verify or re-establish this invariant. If a future bug, hand-written test, or new pass produces an unrounded f64 value tagged as F32, FCmp and FloatToInt will silently diverge from runtime.

The M-E and M-F audit tests pass *because* M-1 is correct. Defense-in-depth would be cheap: round through f32 in both folds when the source operand carries `F32`. The agent's pass-1 finding actually called for this; the team chose to rely on the invariant instead.

### B-4 — `find_natural_loops` body computation can escape the loop in irreducible CFGs

**File:** `src/opt/util.rs:298-307` (pre-existing, but exposed by the M-7 fix's framing)

The BFS walks `preds(latch)` and stops only at `header`. It does **not** check that walked nodes are dominated by `header`. For any CFG with an "outside" predecessor of a body block (i.e., an irreducible loop or a goto-into-loop pattern), the BFS escapes the loop and adds non-loop blocks to `body`. LICM would then refuse to hoist (because `loop_defs` is too large) — a missed optimization, not a wrong-result.

In Fortran-frontend output today, this can't be triggered because the lowerer only emits reducible loops. Worth noting for future GOTO/error-recovery handling. Not introduced by the M-7 fix; M-7 just touched the same code.

### B-5 — DCE block-param removal is O(N²·K) per outer iteration

**File:** `src/opt/dce.rs:248-265`

```rust
for (target_block, mut idxs) in by_block {
    idxs.sort_by(|a, b| b.cmp(a));
    for idx in idxs {
        if let Some(blk) = func.blocks.iter_mut().find(|b| b.id == target_block) { ... }
        for src in func.blocks.iter_mut() {
            if let Some(term) = &mut src.terminator {
                drop_branch_arg(term, target_block, idx);
            }
        }
    }
}
```

For each `(target, idx)` pair, the code walks all blocks twice via linear `find`. With N blocks and K total dead params, this is O(N²·K) per outer iteration. The outer loop can fire multiple times. For large functions with many dead block params (which becomes likely once mem2reg lands), this will dominate compile time.

Performance issue, not correctness. Fix: build a `BlockId → index` map once.

### B-6 — Operand-walking code is duplicated five ways

**File:** `src/opt/util.rs:13-58`, `src/opt/dce.rs:76-150`, `src/opt/cse.rs:159-220`, `src/opt/const_prop.rs:121-132`, `src/ir/verify.rs:294-370`

`inst_uses`, `terminator_uses`, `terminator_targets`, and `prune_unreachable` are duplicated across five files. Adding a new `InstKind` variant (likely soon — atomics, intrinsics, vector ops) requires updating all five. Missing one would silently break that pass.

Pre-existing maintenance footgun, but the team's "fix" added a sixth duplicate (`substitute_in_inst`/`substitute_in_terminator` in cse.rs) instead of consolidating. Worth a one-shot refactor pass.

## NEW minor issues

### B-7 — CSE chase-pointer logic is dead code in practice

**File:** `src/opt/cse.rs:255-262`

```rust
let keys: Vec<ValueId> = rewrite_map.keys().copied().collect();
for k in keys {
    let mut cur = rewrite_map[&k];
    while let Some(&next) = rewrite_map.get(&cur) {
        cur = next;
    }
    rewrite_map.insert(k, cur);
}
```

In local CSE, every `rewrite_map` entry is `(duplicate_id → first_occurrence_id)` where `first_occurrence_id` is, by construction, never itself a key (it's the *first* occurrence in its block). So the chase-pointer loop never iterates more than zero steps. The code is correct and harmless but its comment ("CSE never produces cycles") implies the chase is necessary, when it's actually dead.

Termination is guaranteed even if entries did chain — strict ValueId decrease.

### B-8 — CSE Key for ConstInt does not normalize value at width

**File:** `src/opt/cse.rs:74`

```rust
InstKind::ConstInt(v, _) => mk(1, vec![], *v),
```

Two equivalent constants stored at different bit-patterns at the same width fail to dedupe. Example: `ConstInt(255, I8)` and `ConstInt(-1, I8)` are semantically the same value (sign bit set in i8) but key differently. Lower.rs may emit either form depending on the source literal.

Missed-optimization, not correctness. Fix: key on `norm(v, w)` for ConstInt.

### B-9 — `substitute_uses_batch` closure contract is fragile

**File:** `src/opt/cse.rs:274-288`

```rust
fn substitute_uses_batch(func: &mut Function, rewrites: &HashMap<ValueId, ValueId>) {
    let r = |v: &mut ValueId| { ... };
    for block in &mut func.blocks {
        for inst in &mut block.insts {
            substitute_in_inst(&mut inst.kind, r);
        }
        ...
    }
}
```

`r` is passed by value into multiple `substitute_in_inst` calls inside a loop. This works **only because** `r` happens to be `Copy` (it captures `&HashMap`, which is `Copy`). If a maintainer ever changes the capture (e.g., to track stats with `RefCell` or to mutate a counter), the closure stops being `Copy` and the loop fails to compile — but only because of the existing borrow checker, not the contract documentation. The signature `mut r: impl FnMut(&mut ValueId)` does not communicate the implicit `Copy` requirement.

A more honest signature would be `r: &mut impl FnMut(&mut ValueId)`. Same for `substitute_in_inst` and `substitute_in_terminator`.

### B-10 — `drop_branch_arg` silently no-ops on out-of-range index

**File:** `src/opt/dce.rs:273-290`

```rust
Terminator::Branch(d, args) if *d == target => {
    if idx < args.len() { args.remove(idx); }
}
```

The defensive `idx < args.len()` is good belt-and-suspenders, but a silent no-op would hide a real bug — a mismatch between the target's params and the predecessor's args is *itself* an IR validity violation (the branch arg list should always match the target's param count). If this branch ever fires, we should at least debug-assert.

Recommendation: `debug_assert!(idx < args.len(), "branch arg list out of sync with target params")`.
