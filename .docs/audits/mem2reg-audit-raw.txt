## Section 1: mem2reg correctness

**M-1. (Major, latent) Unreachable store-block + reachable join produces invalid IR.**
`promote_function` scans every block for stores at `mem2reg.rs:114-122`, including blocks unreachable from the entry. `compute_dominance_frontiers` at `walk.rs:500-535` also walks every block's preds unconditionally, so an unreachable predecessor of a reachable join ends up with the join in its DF. The rename walk runs over the dominator tree only (`dominator_tree_preorder` / `rename_block`), which by construction skips unreachable blocks — so the unreachable pred's branch args are never extended. The verifier's `check_branch_args` will reject the IR ("expected N+1, got N"). Two mitigations are available: call `prune_unreachable` at the top of `promote_function`, or skip stores found in unreachable blocks when building `store_blocks`. Currently neither is done. Current Fortran lowering doesn't produce unreachable blocks that ALSO store to a promotable alloca AND branch into the reachable join, so this is latent — but it's the exact kind of bug that only surfaces when an upstream pass introduces dead code and a later compile trips on it.

## Section 1: mem2reg correctness

### M1 (MAJOR — latent): mem2reg produces invalid IR when a store-containing unreachable block has a branch into a reachable join point

`find_promotable_allocas` and `store_blocks` collection at `src/opt/mem2reg.rs:114-122` walk **every** block regardless of reachability. `compute_dominance_frontiers` at `src/ir/walk.rs:500-535` does the same: it walks every block as a join candidate and, for each pred, walks idoms upward. When the pred is unreachable (has no idom), the loop adds `x` to `df[unreachable_pred]` once and then bails. The iterated-DF closure in mem2reg (`src/opt/mem2reg.rs:128-146`) then pulls that reachable join `x` into `phi_blocks` for any alloca stored to from the unreachable block.

mem2reg inserts a new `BlockParam` at `x` (line 230-237). The rename walk, driven by `dominator_tree_children`, visits only reachable blocks, so the unreachable pred never has its branch-args updated. The resulting IR has `target.params.len() == N+1` but the unreachable pred's `Branch(x, args)` still has `args.len() == N`. The verifier's `check_branch_args` (`src/ir/verify.rs:241-247`) rejects this: `branch ... expected N+1, got N`.

Trigger requires: (a) an unreachable block that stores to a promotable alloca AND (b) that same unreachable block branches into a reachable join point. Neither the Fortran lowerer nor any existing pass produces this today, so no existing e2e test triggers it — but any future pass that creates temporarily unreachable blocks mid-module (a shape `prune_unreachable` expects to handle gracefully) will trip this. The cheap mitigation would be to call `prune_unreachable(func)` at the top of `promote_function`, or to filter unreachable blocks out of `store_blocks`. Neither is done.

### M2 (MAJOR — latent): mem2reg double-appends branch args when a CondBranch's two arms target the same block

`src/opt/mem2reg.rs:346-377`, the rename walk, computes successors as a plain vec:

```rust
Some(Terminator::CondBranch { true_dest, false_dest, .. }) => {
    vec![*true_dest, *false_dest]
}
```

then iterates each succ and calls `append_branch_args_for`. `append_branch_args_for` (line 507-524) is *symmetric* — for a `CondBranch`, a single call extends **both** `true_args` AND `false_args` if they match `target`. So if `true_dest == false_dest == B`, the outer loop iterates twice with `succ = B`, and each call extends both arg lists, resulting in each being appended TWICE. Result: `true_args.len() == false_args.len() == 2 * target.params.len()`, which the verifier rejects.

The same trap applies to `Switch` terminators with duplicate case targets, though mem2reg's `append_branch_args_for` short-circuits Switch at line 520-522. For CondBranch, the bug is live.

Not currently exercised because the lowerer and existing passes don't produce same-target CondBranches. const_prop folds constant cond into a plain `Branch`. But any pass that collapses arms later (e.g., a future jump-threading pass) will trip this. Fix: dedupe `successors` before iteration, or have the successor loop skip a target it's already processed.

### M3 (MEDIUM — missing coverage): no test for multiple stores per iteration in a loop

The existing `loop_counter_promoted_with_header_param` test stores `next = cur + 1; store next, slot` exactly once per iteration. The pass DOES handle multiple stores per iteration correctly — each store pushes onto the stack, and the back-edge branch arg uses the final stack top — but the test doesn't pin it. If the rename walk ever regressed to picking the wrong store as the "current" value, no test would catch it.

### M4 (MEDIUM — missing coverage): no test for nested loops with separate promoted counters

The outer-counter-plus-inner-counter shape exercises: (a) two separate header block params, (b) inner-loop stack pushes popping correctly back to the outer scope, (c) the outer header's phi using the outer counter, NOT the inner counter. All handled by the current stack-discipline, but entirely untested.

### M5 (MEDIUM — missing coverage): no test for two allocas with phi placements at the same block

`block_phi_order` maps block → ordered list of alloca indices. Order is "sorted by promotable index", which in turn is "order the alloca appears in the function". If two allocas both need phi params at block B, they're appended in that fixed order. The rename walk uses the same `block_phi_order` when appending branch args at predecessors, so order is consistent. Correct by construction, but not pinned by any test.

### M6 (MEDIUM — missing coverage): no test for the "load-only, no store" alloca case

A read-only alloca should still be removed. The pass handles it: Undef inserted, load rewrites to Undef, dead_loads contains the load, alloca_ids contains the alloca. The retain drops all three. The existing `load_before_any_store_reads_undef` test exercises load-then-return, but the instruction sequence doesn't walk the "alloca with no stores at all" specifically — both paths share the same code. Worth pinning.

### M7 (MEDIUM — missing coverage): no post-mem2reg verifier invocation on a loop IR

`loop_counter_promoted_with_header_param` calls `verify_module` (line 827), which is the only loop-shape verification. A diamond-inside-loop (back-edge PLUS inner-if-else) isn't covered. Iterated DF on that shape should insert phis at both the inner merge AND the loop header, and branch args should flow to both. Entirely reasonable that the pass handles it, but untested.

### M8 (MINOR — no harm, just wasteful): Undefs inserted for write-only allocas are later DCE'd

For an alloca that's stored-to but never loaded, mem2reg still inserts an Undef sentinel (line 187-205). That Undef is never consumed; DCE later removes it. Not a bug, just wasted work — a trivial early-out "skip undef insertion if the alloca has no loads in the function" would save a small constant.

### M9 (MINOR — DF corner case): entry block self-loop is not in its own dominance frontier

`compute_dominance_frontiers` at `src/ir/walk.rs:515` skips blocks with `|preds| < 2`. A single-block function with a self-branch (`Branch(entry, [])`) has `preds(entry) = [entry]` and is skipped, so `DF(entry) = ∅`. Per the mathematical definition, entry IS in `DF(entry)` (entry dominates a pred of itself, and entry does not *strictly* dominate itself). Mem2reg won't try to place a phi there because no store block would ever iterate onto this empty DF, and the entry-block skip on line 222 would cover it anyway. Not exploitable in practice, but worth a comment or test if compute_dominance_frontiers is ever used outside mem2reg.

## Section 2: Dominator tree / DF correctness

### D1 (MAJOR — latent): `compute_immediate_dominators` is O(|V|^3) and iterative search is algorithmically wrong in pathological CFGs

At `src/ir/walk.rs:450-458`, the idom of `B` is found by testing every candidate `cand` in `B`'s dominator set for the property "every other candidate other dominates cand". This is correct for the **unique** idom that exists, but the linear `find` returns the FIRST matching candidate, not the closest. In well-formed reducible CFGs the idom is unique and this succeeds, but:

- **Performance**: this is O(|doms(B)|^2) per block, which becomes O(|V|^3) for the function. Fine for small Fortran routines, slow for large ones. LLVM uses Lengauer-Tarjan for O(|V|·α(|V|)).
- **Correctness edge case**: if the code walks an unreachable component where `compute_dominators` returned an empty set (`|doms| == 0`), the candidate filter produces an empty list and `find` returns None. Line 460-462 handles this by not inserting the idom. Good.

Not a bug for correctness today, but a known O(|V|^3) scaling worth noting.

### D2 (MEDIUM — test-only): the walk_tests suite has no test for irreducible CFGs

Irreducible CFGs (two blocks that branch to each other without a clear header) aren't producible from Fortran lowering today, but `compute_dominators`, `compute_immediate_dominators`, and `compute_dominance_frontiers` are public API. A test that constructs an irreducible two-block component and asserts both blocks are properly dominated (or correctly marked unreachable if there's no entry path) would lock in semantics. Absent that, future changes could silently break the guarantees.

### D3 (MEDIUM — missing coverage): no test for multi-latch loops

A loop header reached from two distinct latches (e.g., a `continue` inside an if/else inside the loop body, producing two back-edges). `find_natural_loops` already groups by header (line 339-342 of walk.rs), but mem2reg on this shape isn't tested. The iterated DF correctly propagates through multiple latches, but the back-edge branch args flow from each latch independently during the rename walk, and the test doesn't pin that.

### D4 (MINOR): `dominator_tree_children` uses an iterative DFS via `stack.pop()`+`rev()` but doesn't document why

`dominator_tree_preorder` at walk.rs:548-559 walks via a work-stack. Children are pushed in reverse so that `.pop()` visits the smallest-BlockId first. This is deterministic and correct, but the code comment "Push in reverse so that smaller BlockId.0 is visited first" is the ONLY hint. If someone refactors to a functional-style recursion, determinism would slip through the cracks. Not a bug, just brittle.

## Section 3: isel branch arg parallel copy

### P1 (MEDIUM — latent): shim block label uniqueness is only guaranteed per-source block

# Brutal mem2reg audit findings

## Section 1: mem2reg correctness

**M1 (Critical, latent) — mem2reg + unreachable blocks → potentially invalid IR**

`find_promotable_allocas` and `store_blocks` walk **every** block in `func.blocks`, including unreachable ones. `compute_dominance_frontiers` in `walk.rs` also starts from every join point and walks up via idoms, but `idoms` only contains reachable non-entry blocks. When a reachable join X has an unreachable predecessor P, the DF walk at `walk.rs:519-530` starts `runner = p` and immediately adds `X` to `df[P]`, then looks up `idoms.get(&P) = None` and breaks. So `X ∈ DF(unreachable_block)`.

If an unreachable block contains a store to a promotable alloca, the iterated-DF closure in `mem2reg.rs:128-146` will add X (a reachable join) to `phi_blocks[idx]`. mem2reg then inserts a block param at X. The rename walk is a DFS over the dominator tree which does **not** visit unreachable blocks, so the unreachable predecessor's terminator args are **never updated**. The verifier's `check_branch_args` rejects any branch whose arg count ≠ target params count.

Result: mem2reg can produce IR that the verifier rejects, on any input that has a store to a promoted alloca inside an unreachable block. The Fortran lowerer typically doesn't emit unreachable blocks with stores, but dead-code reachable via `GOTO` after STOP and const-folded conditionals can produce them. No test covers this. Fix: either prune unreachable blocks at the start of `promote_function`, or filter `store_blocks` to only reachable blocks (and skip unreachable preds in the rename walk's updates). Path: `src/opt/mem2reg.rs:113-122`.

**M2 (Critical, latent) — double-append when CondBranch has same target on both arms**

`rename_block` builds successors as `vec![*true_dest, *false_dest]` (`mem2reg.rs:351-353`) without deduplication. If a block's terminator is `CondBranch { true_dest: B, false_dest: B, .. }`, the successor loop visits `B` twice. Each call to `append_branch_args_for` at `mem2reg.rs:507-524` matches BOTH `true_args` and `false_args` arms (line 513-518), so each visit extends each arg list once. After two visits, both `true_args` and `false_args` are `2 * new_args` long. The verifier will reject as a branch-arg count mismatch.

This shape isn't produced by today's frontend or by const_prop (which folds same-target CondBranch into `Branch`), but there is no pass that guarantees it cannot arise, and a future pass (e.g., jump threading) could legitimately generate it. No test covers it. Fix: `successors.dedup()` after building, or change `append_branch_args_for` to idempotently match at most one arm when both equal the target. Path: `src/opt/mem2reg.rs:346-360`, `:507-524`.

**M3 (Major) — no test pins "only-loaded alloca" promotion**

The task description mentions this as an expected behavior, but no test in `mem2reg.rs::tests` exercises it. The `load_before_any_store_reads_undef` test only has one load, and it's the only use; it doesn't exercise the combination of "load before any store, then later also loads in a different path." I read the code and believe it's correct, but the promotability check + rename walk for an alloca with only loads (no stores at all) has zero coverage. `store_blocks[idx]` would be empty, iterated-DF closure inserts nothing into `phi_blocks[idx]`, rename walk sees stack = `[undef]` at every load, all loads rewrite to undef. Should be fine, but not pinned.

**M4 (Major) — no test pins nested loops with independent allocas**

Nested counter loops (`do i; do j; end do; end do`) are a standard mem2reg workload. The test suite has one flat loop test (`loop_counter_promoted_with_header_param`). No test verifies that two independent promotions targeting different natural loops produce block params on their respective headers without cross-contamination. No bug found by reading code, but it's a large gap in the test matrix given the "per-alloca current-value stack" design.

**M5 (Major) — no test pins multiple-stores-per-iteration**

The loop test does one store per iteration (`i = i + 1`). A loop body with two stores to the same alloca (`x = ...; x = ... + 1;`) exercises the "second push then pop at block exit" pop sequence. No test covers it. No bug found, but coverage gap.

**M7 (Major) — no test pins two allocas with phi at the same block**

When two allocas both need a phi at the same join block, mem2reg inserts two block params. The test suite only exercises one promotable alloca per test. The `block_phi_order[block]` ordering determines arg order, and the iteration at `mem2reg.rs:219-237` sorts blocks per alloca but processes allocas in index order — this produces `block_phi_order[B] = [idx_0, idx_1, ...]` in deterministic order. ## Section 2: Dominator tree / DF correctness

**D1 (Minor) — self-loop on entry creates a DF edge case**

`compute_dominance_frontiers` at `walk.rs:512-515` skips any block with fewer than 2 predecessors. By the mathematical definition, a block with a single self-loop (preds = `[self]`) IS in its own dominance frontier (self dominates a pred of self, self doesn't strictly dominate self). Cytron's published algorithm also misses this, so it's not a novel bug, and it only matters if the entry block has a self-loop — which the verifier doesn't currently reject but which never arises from the frontend. Cosmetic.

**D2 (Major) — compute_dominance_frontiers walks unreachable predecessors**

At `walk.rs:519-530`, the DF walker iterates over `preds.get(&x)` which includes unreachable predecessors. For an unreachable `P`, `idoms[P]` is absent, so the loop body adds `x` to `df[P]` and then breaks at `None`. That populates `df[unreachable_block]` with entries that then participate in mem2reg's iterated-DF closure. This is the upstream source of M1 above. Fix at the source: filter `plist` to reachable preds (using the same reachability set `compute_dominators` already computes internally — that set isn't currently exposed).

**D3 (Major) — no tests for multi-latch loops, irreducible CFGs, unreachable components, single-block functions**

The `walk_tests` module has exactly five tests: diamond (idoms + DF), diamond preorder, simple loop DF, nested-if DF. Missing:
- Multi-latch loop (two back-edges into the same header).
- Irreducible CFG (two blocks that branch to each other, neither dominates).
- Unreachable component (a block not reachable from entry).
- Function with exactly one block and no terminator targets.
- Self-loop on a non-entry block.

Any of these could harbor a subtle bug in `compute_immediate_dominators` (the "find the dominator that has the largest dom set" search at `walk.rs:450-458` is O(n²) and assumes a specific dominance lattice shape) or in `compute_dominance_frontiers`. Without tests, nothing anchors these behaviors.

**I4 (Major) — shim block's CFG predecessor tracking relies on liveness's instruction-scan**

`liveness.rs:66-90` builds the successor map by scanning every instruction in every block for `B`/`BCond` opcodes. But note: the shim block is `mf.new_block`'d and appended at the END of `mf.blocks`. The backward dataflow in liveness iterates `mf.blocks.iter().rev()` at line 96. Because the shim block is appended LATE, it appears near the end, and the backward iteration visits it early. But the fixpoint convergence depends on iteration order for SPEED, not correctness — eventually it's right. OK.

However, what's NOT verified is that the shim block's source-vreg uses are counted in the source block's live_out. Because the shim is the direct successor of the source, `live_out(source) ⊇ live_in(shim)`, which includes the shim's src_vregs. Correct. But there's no test that exercises this flow under spill pressure. If a src_vreg is spilled, apply_allocation must emit a load before the shim's use of that vreg — does it? apply_allocation walks every block, including shims, and inserts loads for spilled vreg operands. Should be correct. Not explicitly tested.

**I5 (Cosmetic) — shim block label collision risk across sibling compiles**

Labels are formatted as `L{mb.0}_true_shim` / `L{mb.0}_false_shim`. `mb.0` is unique within a function, so no intra-function collision. But the label has no function-name prefix, so if the assembler ever gains the ability to merge functions... irrelevant today. Noted.

## Section 4: Phase 4a/4b split

**P1 (Minor) — Phase 4a class mismatch potential for ConstBool/ConstInt**

Phase 4a uses `type_to_reg_class(&inst.ty)`. Phase 4b's `select_inst` passes a class that depends on the specific instruction:
- `ConstInt` → `int_width_class(width)` vs `type_to_reg_class(Int(w))`. Both return Gp32 for ≤ I32, Gp64 for I64. Match.
- `ConstBool` → `Gp32` hardcoded vs `type_to_reg_class(Bool)` = Gp32. Match.
- `ConstString` → `Gp64` hardcoded vs `type_to_reg_class(Ptr(I8))` = Gp64. Match.
- `ConstFloat` → `float_width_class(w)` vs `type_to_reg_class(Float(w))`. Match.
- `ICmp`/`FCmp` → `Gp32` (result type Bool) vs `type_to_reg_class(Bool)` = Gp32. Match.

I don't find a concrete mismatch. But the invariant is spread across two tables (`type_to_reg_class` and the per-instruction class choices) and a future edit could introduce a mismatch. When the mismatch happens, Phase 4a's class wins (because `get_vreg` lookups succeed first) and Phase 4b's class is silently ignored. That produces a vreg of the "wrong" class for one specific instruction — potentially assigning an FP value to a GP register or vice versa. Worth adding an `assert!(existing.class == requested_class)` inside `ISelCtx::get_vreg`.

**P2 (Cosmetic) — Phase 4a clones every block's params + insts to compute `func_blocks`**

`isel.rs:156-158`: `ctx.func_blocks.insert(block.id, block.clone());` clones the entire `BasicBlock` for every block. For a large function (1000s of blocks), this is unnecessary memory pressure — only `params` is actually read by `emit_branch_arg_copies`. Could be reduced to cloning just the `params` vec per block. Micro-optimization.

**P3 (Minor) — Phase 4a skips Undef vregs? No, it includes them**

I initially worried that Undef's `Void`-typed skip might drop them. Undef has type `p.pointee_ty` (never Void). Phase 4a at line 146 skips Void, which is only Store and void-returning Call/RuntimeCall. Undef is included. Good. But the Undef vreg has no define-point in the machine code — `InstKind::Undef` handler at isel.rs:271-275 emits no instruction. The liveness analysis then has a vreg whose only "definition" is via live-in propagation to the entry block. Linearscan assigns it a register that is never written. On ARM64 Apple, the initial contents of allocated but unwritten registers are whatever the caller left behind, which is correct undef semantics but means any spilled/non-callee-saved reg might contain arbitrary data. Correct, but relies on downstream undef semantics not being strict. This exact behavior is what exposes the separate **parameter-lowering bug** (see Section 6).

## Section 5: Determinism

**Det1 — liveness sort tiebreak fix is correct**

`liveness.rs:211`: `intervals.sort_by_key(|i| (i.start, i.vreg.0))`. Since `vreg.0` is unique per interval, the key is unique and the sort is fully deterministic. Verified.

**Det2 — linearscan active list fix is correct**

`linearscan.rs:69-70`: `active_gp: Vec<(u8, u32, VRegId)>` replaces the old `(u8, u32)` tuple. Spill-victim selection at line 141 now reads the `VRegId` directly from the active list instead of scanning `assignments` HashMap. The active list is populated in the order of `liveness.intervals` iteration (deterministic from Det1), so ordering is stable. Verified.

**Det3 — `apply_allocation` fix is correct**

`linearscan.rs:231-234` sorts `result.assignments` by `vreg.0` before building `gp_temps`/`fp_temps`. Good.

**Det4 (Minor) — callee_saved_used still goes through a HashSet + sort**

`linearscan.rs:73, 178-183`: `callee_saved_used: HashSet<PhysReg>` is then collected and sorted by a key that maps `Gp(n)` and `Gp32(n)` to the SAME value `n as u16`. If both variants of the same register number were ever inserted (shouldn't happen in practice — callee-saved are assigned as 64-bit containers), the relative order of `Gp(5)` vs `Gp32(5)` would be unstable because `sort_by_key` is stable but `into_iter` on a HashSet is NOT stable. Theoretical, not actual.

**Det5 (Major, not verified) — no determinism test added to the test suite**

The audit claims "5/5 identical MD5s on select_type.f90" but this is a manual check, not a committed regression. A determinism regression could reintroduce nondeterminism after a future edit. The test harness (`run_programs.rs`) has no "compile twice, compare bytes" mode. Recommend adding a dedicated determinism test that compiles 2-3 representative programs twice and diffs the assembly output. Otherwise this class of bug will silently return. Path: `tests/run_programs.rs`.

**Det6 (Minor) — HashMap iteration in emit path was NOT audited explicitly**

I didn't trace every HashMap in `emit.rs`. Grep confirms `emit.rs` uses no HashMap directly, walking `mf.blocks` and `inst.operands` in deterministic order. Safe.

**Det7 (Minor) — LICM, CSE, DCE HashMap iteration after mem2reg**

Grep shows `opt/licm.rs:163` (`block_index: HashMap<BlockId, usize>` — lookup only), `opt/licm.rs:210` (`by_block: HashMap<usize, Vec<usize>>` — **iterated for removal**). Let me look more carefully:

=== MESSAGE BREAK ===

**DETERMINISM CONCERN — LICM iterates `by_block` HashMap at line 221.** The iteration order is non-deterministic. But the iteration only REMOVES instructions from `func.blocks[bi]`, and each block's removals are sorted descending before application. The order of blocks being processed doesn't affect the final `func.blocks` state — each block's removals are independent. **Safe.** Good.

**Det8 — DCE HashMap iteration**

=== MESSAGE BREAK ===

**DCE `by_block` HashMap** — same as LICM. Iterated at line 161 of dce.rs. Let me check.

=== MESSAGE BREAK ===

**CRITICAL — DCE's `remove_dead_block_params` iterates `by_block` HashMap in non-deterministic order at line 161.** Different iteration orders mean the blocks are processed in different orders. Each block's removal operation:
1. Removes the param at `idx` from target_block.
2. For EVERY source block's terminator that branches to target_block, drop the arg at `idx`.

Because each block's processing mutates ALL source terminators (not just predecessors), there's a CROSS-BLOCK effect. If block B has params [p0, p1] and block C has params [q0, q1, q2], and we delete p0 then q1, we remove idx 0 from B's params and idx 1 from C's params, plus adjust the corresponding args in every predecessor. If we delete q1 first then p0, we do the same operations in reverse order. Does order matter?

Consider a block A whose terminator is `Branch(B, [a, b])` and also `Branch(C, [c, d, e])`. We delete p0 (B's first param) → Branch(B, [b]). Then delete q1 (C's second param) → Branch(C, [c, e]).

Reverse order: delete q1 first → Branch(C, [c, e]). Then delete p0 → Branch(B, [b]). Same final result.

But... indices into C are affected by C's own prior deletions. If DCE deletes q1 then q0 in that order, q0 is at index 0 of the now-shortened C.params. If DCE deletes q0 then q1, after removing q0 the original q1 is at index 0. **This changes which param is "q1".** But wait — `idxs` is sorted DESCENDING before the inner loop (line 162), so within a single block we delete high-idx first. Order preserved.

But across blocks, the HashMap iteration order varies. If blocks B and C are processed in different orders... Within each block's processing, the inner loop is deterministic. The `for src in func.blocks.iter_mut()` at line 174 rewrites ALL terminators, so there's no "later block fixes what earlier block broke" concern.

**Hmm, actually the order doesn't change the final state for block param removal.** Each block's params are independently identified as dead (via `live` set), and the deletions are keyed by `(target_block, idx)` pairs. The set of pairs is fixed. The only question is: are the terminators in source blocks left in the same final state regardless of processing order?

Consider source block A with `Branch(B, [x, y])` and `Branch(C, [z])`. Wait, a block can only have ONE terminator. OK so A branches to at most TWO targets (via CondBranch). Each target's arg list is independent.

If A is `CondBranch { true: B, true_args: [x, y], false: C, false_args: [z, w] }` and we delete B's param 0 and C's param 1:
- Delete B first: CondBranch { true: B, true_args: [y], false: C, false_args: [z, w] }.
- Then delete C's param 1: CondBranch { true: B, true_args: [y], false: C, false_args: [z] }.
- Reverse: delete C first, then B. Same final.

**Good — DCE's cross-block HashMap iteration is commutative. Deterministic output.**

But what if a single CondBranch has `true: B, false: B` (same target both arms)? Then processing B's params affects BOTH `true_args` and `false_args`. `drop_branch_arg` at line 194 — let me check.

=== MESSAGE BREAK ===

Good. `drop_branch_arg` handles CondBranch with same target for both arms by checking both arms. Still safe.

**Det9 — const_prop, strength_reduce HashMap iteration**

Both collect_consts and collect_int_consts build HashMap keyed by ValueId, LOOKED UP (not iterated) later. Safe.

**Det10 — cse `substitute_uses_batch`**

=== MESSAGE BREAK ===

CSE's `rewrite_map` is a HashMap, iterated only by `substitute_uses_batch` which applies to every operand. The iteration order doesn't affect the result because each (old, new) mapping is applied independently. Good.

## Section 6: Parameter lowering exposure

**P-Low-1 — No other test programs use `parameter ::`**

Grep across `test_programs/*.f90` found ONLY `const_prop.f90` references `parameter`, and that's in a comment explaining the rewrite. No other test program depends on the broken parameter lowering. No hidden exposure.

**P-Low-2 — The noted issue correctly captures the bug**

`.docs/noted_issues.md:103-114` documents the parameter-lowering bug. The fix is scheduled but not implemented. Correct.

**P-Low-3 (Major) — DEFERRED FIX LEAKS THROUGH TO USER-WRITTEN CODE**

Any Fortran program that uses `logical, parameter :: foo = .true.` will **silently miscompile** at -O1 and up. The condition reads undef, codegen assigns an arbitrary register, the branch flips based on arbitrary garbage, and the program takes an unpredictable path. For a program that isn't in our test_programs/ directory, there is NO warning. This is classified as "D — scheduled for cleanup" in noted_issues, but the bug produces **wrong answers silently on a standard F77 feature**. Per the audit brutality guidance, this should be re-classified as **critical, fix now**, not deferred. A comment-documented bug is still a shipped bug.

Concrete example to verify the severity:
```fortran
integer, parameter :: n = 100
do i = 1, n
  ...
end do
```
The `n` in the loop bound is loaded from an uninitialized stack slot. The loop count is essentially random.

## Section 7: Cross-pass interactions

**X1 (Minor) — No integration test verifies const_fold propagates through former locals**

Mem2reg unlocks const_fold for local variables. The claim: `x = 5; y = x * 2 + 3` should fold to `const 13`. Neither const_fold's own tests nor the e2e test suite verifies this end-to-end (at the IR level). The e2e tests only check program output. You could in principle fold incorrectly AND still produce the right output by coincidence. Adding an IR-dump snapshot test would pin this.

**X2 (Minor) — LICM + mem2reg interaction untested**

After mem2reg, LICM should be able to hoist loop-invariant pure computations that used to be blocked by loads. `test_programs/licm_invariant.f90` exists but doesn't specifically target the "mem2reg unlocked this" pattern. Is the hoisting actually happening? No IR-level assertion verifies it.

**X3 (Major) — CSE may now key incorrectly on mem2reg-created block params**

CSE's `key_of` (not shown, but in cse.rs) extracts a deterministic key from an instruction. Block params are not instructions, but they DO produce ValueIds. If CSE keys an instruction by `InstKind + operand ValueIds`, and a block param and an instruction result happen to be "equivalent" in some semantic sense, CSE treats them as distinct (correct — they have different ids). I verified by reading cse.rs that block params aren't considered. Should be safe.

**X4 (Cosmetic) — DCE runs AFTER mem2reg; catches dead Undef sentinels**

When mem2reg inserts Undefs that nothing ends up using (e.g., write-only allocas), DCE removes them. Good.

**X5 (Major, untested) — const_fold and undef operand interaction**

`const_fold.rs:57` — `Const::from_inst` returns `None` for Undef. const_fold therefore never tries to fold an `IAdd(undef, const)` into anything. The IAdd is left alone. `ConstFold` doesn't treat undef as "we can pick any value." That's the SAFE behavior — but it also means const_fold may leave arithmetic that could be folded if undef were treated as "pick zero". That's fine; LLVM does the same. Not a bug, just an optimization opportunity we're not taking.

## Section 8: Things missed / new findings

**N1 (Critical) — Mem2reg does NOT run the verifier itself; relies on PassManager**

The tests at `mem2reg.rs::tests` explicitly call `verify_module` after `Mem2Reg.run`. But in the normal pipeline, `PassManager.run` calls `verify_module` after every pass. If a pass emits invalid IR, PassManager panics with the offending pass name. This is the fallback safety net. But the audit bug M1 (unreachable blocks → invalid IR) would trigger that panic on user input — which, at production time, is a **compiler crash**. Fix: document the reachability precondition explicitly, or prune unreachable at the start of mem2reg.

**N2 (Minor) — Test helper `push_inst` doesn't set inst.ty properly for all variants**

In `mem2reg.rs::tests`, `push_inst` takes `ty` as a parameter. For Store instructions, the test passes `IrType::Void` (correct, Store returns void). But for Alloca, the test passes `IrType::Ptr(Box::new(...))`. That's semantically correct — an alloca produces a pointer. Tests are consistent with the real lowerer's output. OK.

**N3 (Major) — Phase 4a `func_blocks` snapshot is taken BEFORE Phase 4b, but shim block creation in Phase 4b adds new MachineBlock IDs that aren't in func_blocks**

`func_blocks` is keyed by **IR BlockId**, not MBlockId. When a shim block is created via `mf.new_block`, it gets a fresh MBlockId. The shim is NOT an IR block — it has no IR BlockId. `emit_branch_arg_copies` at line 1086 does `ctx.func_blocks.get(&target_block)` where `target_block` is the IR target (not the shim). This works because the shim is not the target; the real IR block is. Good.

But there's a subtle edge case: what if `emit_branch_arg_copies` is called with a shim as the `mb` (machine block)? Look at line 975: `emit_branch_arg_copies(mf, ctx, shim, *true_dest, true_args);`. The `mb` parameter is the shim. The `target_block` is the real IR target. The function emits moves into the shim's inst list. This is correct — moves go into the shim, and the shim branches to the real target. ✓

**N4 (Major) — `emit_branch_arg_copies` panics on mismatched arg count**

At line 1088-1094, the function panics if `args.len() != target_func_block.params.len()`. This would only happen on invalid IR (caught by verifier). But mem2reg's M1 (unreachable blocks) and M2 (same-target CondBranch) bugs above could produce exactly this mismatch and drive isel into this panic. Compiler crash on invalid user input.

**N5 (Minor) — `ISelCtx::lookup_vreg` panics on unmapped IR value**

Line 213-216 panic is a valid assertion, but with mem2reg now introducing Undef and block params, any slip in the pre-allocation logic crashes isel. On first mem2reg deploy, this is the most likely place a mem2reg-produced ValueId would surface: mem2reg creates undef_values via `func.next_value_id()`, assigns them to Undef instructions in entry. Phase 4a walks entry.insts including the Undef and allocates a vreg. So the vreg IS created. I traced this. Safe.

But: **are there any mem2reg-created ValueIds that DON'T land in an instruction?** No — every Undef id is placed inside an `Inst {}` in entry. Every block param id is placed inside a `BlockParam {}` in the target block. Both are reachable by Phase 4a's walk. Safe.

**N6 (Major) — Mem2reg insertion of Undef at entry[0..N] violates SSA "def before use" for the terminator itself if entry has only a terminator and no insts**

If entry has no insts before mem2reg runs (only a terminator), the `span` lookup at line 168-185 falls through to the zero span. No bug there. And Undef insertion at `pos = 0, 1, 2, ...` works on an empty insts vec. But what if the ENTRY BLOCK'S TERMINATOR references a ValueId that was a `load(alloca)` hoisted into entry? That load would be in entry.insts (before terminator). Mem2reg inserts Undef at pos 0 — BEFORE the load. The load is now at pos N (after all Undefs). Load's use of alloca is still valid (alloca is at pos > N, alloca dominates load). After renaming, the load's uses are rewritten to Undef (which is at pos 0). The terminator references the load's original ID (which becomes Undef). Undef at pos 0 dominates the terminator (which is at pos ∞). Verifier satisfied.

But what if the terminator ITSELF references an alloca directly? That's an alloca escape via terminator_uses, so find_promotable_allocas disqualifies it. The alloca is not promoted. Safe.

**N7 (Major) — Determinism check not committed as a regression test**

As noted in Det5. This should be a dedicated test that the CI runs. Otherwise a future HashMap introduction silently breaks determinism and we find out when a flake resurfaces.

**N8 (Cosmetic) — `crate::lexer::Span` / `Position` inlined in mem2reg.rs**

At `mem2reg.rs:173-185`, the code manually constructs a zero-span. This is the kind of copy that drifts. Minor, but a `Span::zero()` helper would be cleaner.

**N9 (Minor) — Two unused-import warnings from cargo test**

Running `cargo test -p armfortas opt::mem2reg` surfaces:
```
warning: unused import: ... in src/opt/mem2reg.rs
warning: unused import: `IntWidth` in src/ir/walk.rs:565:39
```
These are just warnings but are new noise.

**N10 (Major) — No tests at -O3/-Ofast for the full test_programs suite**

The e2e runner has three tests: `test_programs_end_to_end` (-O0), `_o1` (-O1), `_o2` (-O2). Mem2reg is wired into O1/O2/Os/O3/Ofast. The full test suite at O3 and Ofast is never exercised. A latent bug that only fires under O3's future vectorization passes wouldn't be caught.

**N11 (Cosmetic) — clippy::too_many_arguments suppression in mem2reg.rs**

`rename_block` has 11 parameters with `#[allow(clippy::too_many_arguments)]`. The pattern is legitimate (recursive DFS with shared state), but a small `RenameCtx` struct would be cleaner. Not a bug.

**N12 (Minor) — Mem2reg doesn't report which allocas it promoted**

The pass returns only `bool`. For debugging optimizer regressions, it would be helpful to log the promoted alloca names (or at least count). Not a bug, just debuggability.

**N13 (Critical) — `dominator_tree_preorder` is unused**

`dominator_tree_preorder` was added as part of Commit 1 and re-exported in `opt/util.rs`, but mem2reg's rename walk uses its own recursive DFS helper (`rename_block`) which walks `children` directly. The `dominator_tree_preorder` function has no consumers. This is dead API — either mem2reg was intended to use it and the refactor was left incomplete, or it's YAGNI. Audit: unused public API is a maintenance liability. Either use it or delete it.

**N14 (Major, pre-existing) — Verifier does NOT check that entry block has no predecessors**

As noted during my review, `verify.rs:45-52` only checks that entry has no block params. The comment claims "Entry block has no predecessors" but the check is narrower. A front-end that emitted an edge back to entry would pass verification. This is pre-existing, not from mem2reg, but mem2reg's M1 bug is amplified because the verifier can't catch the earlier problem.

## Verdict

⚠ **needs fixes** — the determinism work is solid, the mem2reg algorithm is essentially correct on the happy path, and the isel branch-arg work handles common cases. But I found:

- **2 critical latent bugs in mem2reg** (M1: unreachable block store → verifier rejection / isel panic; M2: same-target CondBranch → double-append)
- **1 critical in determinism hygiene** (Det5: no committed determinism test)
- **1 critical in test coverage** (N10: no e2e at -O3/-Ofast)
- **1 critical in the parameter lowering bug classification** (P-Low-3: should be "fix now," not deferred)
- **1 dead API** (N13: `dominator_tree_preorder` is unused)
- **Major coverage gaps** across nested loops (M4), multi-store-per-iteration (M5), diamond-inside-loop (M6), two-allocas-same-join (M7), multi-latch loops, irreducible CFGs, single-block functions (D3), and `emit_branch_arg_copies` cycles (I1)
- **1 major DF correctness issue** (D2: DF walker populates entries for unreachable predecessors)
- **1 pre-existing verifier gap** (N14: entry-no-predecessors check is only params-no-entries)

The mem2reg + isel changes pass every existing test, including the full e2e at -O0/-O1/-O2 and all 97 opt unit tests. No observed miscompile on today's test programs. But two of the bugs above (M1, M2) can produce invalid IR on inputs the test suite doesn't cover, which will manifest as a compiler panic (internal verifier failure) when a user writes code that triggers them. Ship blockers for compiler robustness but not functional correctness on the current test matrix.

Recommended minimum fixes before declaring the branch shipped:
1. Fix M1 (prune unreachable in mem2reg, or in compute_dominance_frontiers) and add a regression test.
2. Fix M2 (dedupe successors) and add a regression test.
3. Commit a determinism test (Det5).
4. Add -O3 / -Ofast e2e test variants (N10).
5. Fix or delete N13 (`dominator_tree_preorder`).
6. Add the adversarial mem2reg unit tests called out in M3–M8.
7. Re-classify the parameter-lowering bug as critical and schedule it for the next sprint, not "cleanup."
8. Add a dedicated test for `emit_branch_arg_copies` cycle-breaking (I1) — the only production code that exercises it today is accidental test coverage via real programs.
