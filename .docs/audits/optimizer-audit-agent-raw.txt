2. `norm(2147483648, I64)` = `sext(mask(2147483648, 64), 64)` = `-2147483648` (because width >= 64 is a pass-through, and `2147483648 as i64` is already positive, **but** `norm` through `sext` for `bits >= 64` just returns `v` unchanged — so `v = 2147483648` stays positive). OK.

Now the genuinely broken case: **unsigned IntExtend from narrower to same width** — e.g., `IntExtend(av = -1_i8, w = I8, signed = false)`:

1. `mask(-1, 8)` = `255`.
2. `norm(255, I8)` = `sext(255 & 0xFF, 8)` = `sext(255, 8)` = `-1`.

The caller asked for an *unsigned* extend and got back a sign-extended value. Identity unsigned extend is rare but the bug is that `norm` unconditionally sign-extends to the IR's stored form, so a logically-unsigned value is re-signed as it exits. This means a later CSE key-hash or ICmp fold that tries to read back the value as unsigned sees the wrong bit pattern in i64 space.

More concretely: if an `IntExtend(u8 → i32, signed=false)` feeds an `ICmp(Ugt, …)` (which doesn't exist yet, but it will) the result will be wrong. **Fix idea**: store the masked (unsigned) representation in the `ConstInt` when the destination is reached via an unsigned extend, or change the contract so that `norm`'s sign-extension only applies when the IR semantically treats the bits as signed.

Related: `norm` is applied to *every* integer fold result, which conflates "the low-bits that matter" with "how to embed the value in i64." This works only because every downstream consumer re-extends via `sext(av, w.bits())`. Any pass that reads `ConstInt(v, I8)` and does a raw `v as u32` (e.g., `val.count_ones()` in PopCount at line 262) will see the extra bits. **That's actually OK in the current PopCount because it immediately masks** — but the invariant is fragile and undocumented.

### C-A2 — `const_fold::Select` rewrites kind but not the instruction's declared type (`src/opt/const_fold.rs:344-358`)

### M-A1 — `const_fold::Shl/LShr` "shift count ≥ width → 0" does not match AArch64 (`src/opt/const_fold.rs:212-242`)

```rust

    …
    if (0..bits).contains(&bv) { … normal case … }
    // Shift count >= width is implementation-defined
    // in C; AArch64 returns 0. Match that.

}
```

**Severity: MAJOR.**
AArch64 `LSL` (encoded via UBFM) masks the shift amount to `log2(reg_width)` bits — i.e., `amt & 0x3F` for 64-bit and `amt & 0x1F` for 32-bit registers. `lsl w0, w1, w2` with `w2 = 32` produces `w0 = w1` (shift by 0 after masking), **not** zero. Likewise `lsl x0, x1, x2` with `x2 = 64` is identity.

The comment's claim is factually wrong. The current fold disagrees with both AArch64 hardware and `i64::wrapping_shl` (which also masks the amount). Fortran programs that use negative shifts go through `ishft(x, shift)` lowering which builds a `Select(ishl, …) … where the Shl branch is speculatively computed for all shift amounts including large ones`, so a fold that returns 0 for counts ≥ width silently produces a value the runtime would never produce.

Additionally, negative shift counts (`bv = -5`): `(0..bits).contains(&-5)` is false, so this emits `0` — also wrong (on AArch64 the low 5 or 6 bits are taken, so `-5 & 0x1F = 27`, yielding a very different result).

**Fix**: when `(bv < 0) || (bv >= bits as i64)`, either (a) bail (leave the instruction alone — safest; matches SSA and defers to codegen), or (b) mask `bv` by `bits-1` before shifting to match AArch64 semantics. Option (b) is only correct if codegen consistently emits `LSL` (not a `Select` with an out-of-range comparison).

The same bug affects `LShr` (line 229-242), with identical wrong return-0 branch.

### M-A3 — `const_fold` misses all integer intrinsics on any CSE'd-alias operand (`src/opt/const_fold.rs:411-434`)

### M-A4 — `const_fold::IntToFloat` uses `as f64` cast which produces wrong results for i64 > 2^53 (`src/opt/const_fold.rs:291-297`)


### M-A5 — `const_fold::FloatToInt` uses `as i64` for out-of-range values (`src/opt/const_fold.rs:298-319`)


2. `i32::MAX as f64` is exactly `2147483647.0` (exact). Good. But `truncd > hi` is *strict*, so `truncd = 2147483647.0` is accepted. Then `truncd as i64 = 2147483647`. OK.

3. **The real bug**: for `truncd = -9223372036854775808.0` (= i64::MIN exactly), `i64::MIN as f64 = -9223372036854775808.0`. **Recommendation**: grep `FloatToInt` callers in `lower.rs` — if `NINT` or `FLOOR` ever lowers to a plain `FloatToInt` without an explicit rounding pre-step, this fold will silently produce wrong values.

### C-A. `strength_reduce` Identity rewrite for pointer/float/struct results silently drops the instruction
**File**: `src/opt/strength_reduce.rs:305-317`
```rust
Rewrite::Identity { pass_through } => {
    substitute_uses(func, old_id, pass_through);
    let placeholder = match ty {
        IrType::Int(w) => InstKind::ConstInt(0, w),
        IrType::Bool   => InstKind::ConstBool(false),
        _ => continue,
    };
    func.blocks[bi].insts[ii].kind = placeholder;
}
```
**Severity**: CRITICAL.
**Why wrong**: The `substitute_uses` on line 306 has already been called by the time the `_ => continue` branch on line 314 fires. That means for any `Identity` rewrite on a non-int, non-bool type, every use of `old_id` across the entire function has been rewritten to `pass_through`, but the defining instruction at `(bi, ii)` is **left in place unchanged**. That's fine by itself — the defining instruction is now dead code — but the `continue` also bypasses `changed = true` on line 319, so the pass reports "no change" even though it rewrote every use in the function. The pass manager won't re-run DCE; the original instruction keeps defining `old_id` but nothing reads it. Verifier passes (that's fine) but the program keeps a stale computation. More importantly: the uses have been redirected, so any **type mismatch** between `old_id` and `pass_through` becomes a permanent, silent bug. 

Today `rewrite_for` only produces Identity for integer ops on integer types, so this branch is unreachable in practice — but that's luck, not design. The moment anyone adds `fmul x, 1.0` → Identity under fast-math (or `getelementptr x, 0` → identity), the `_ => continue` eats the `changed = true` and also leaves a live substitution with no restore path.
**Repro (if Identity ever fires on a non-int/bool type)**: any float identity rewrite would hit this.
**Fix**: either restrict `rewrite_for` to only emit Identity for int/bool (assert-enforced), or drop the placeholder machinery entirely — you can leave the original instruction alone because `substitute_uses` already rewired the uses and DCE will delete it next round. Also set `changed = true` before the `continue`.

### C-B. `licm::licm_function` keeps an out-of-date `block_index` when preheader isn't the entry
**File**: `src/opt/licm.rs:126-197`
**Severity**: CRITICAL (silently moves instructions into the wrong block).
**Why wrong**: `block_index` is built **once** on lines 126-129 before any loop is processed. But inside the loop body (line 197) we do `let ph_idx = block_index[&ph_id];` and then `func.blocks[ph_idx].insts.extend(extracted);`. Preheader analysis walks `ph_block.terminator` which hasn't moved, so this part is OK. But `loop_defined_values(func, lp)` is computed **per loop** (line 139) from the function's current state. If an earlier loop (sharing a body block with this one, which happens with nested loops) hoisted instructions out of a shared block, those instructions now live in a preheader that may or may not be inside the current loop's body. The `loop_defs` is built on line 139 for L2 and does **not** include the newly hoisted instruction (because that instruction was already originally in L2's body before the hoist), so the invariance check fires and the instruction gets re-hoisted into L2's preheader. After that: B = [a, c], P = [..., b].

## Major bugs

### M-A. `const_fold::FloatToInt` bounds check uses `i64::MAX as f64` which rounds up to 2^63, admitting out-of-range values
**File**: `src/opt/const_fold.rs:298-317`
```rust
let hi = match w {
    ...
    IntWidth::I64 => i64::MAX as f64,
};
if truncd < lo || truncd > hi { return None; }
return Some(InstKind::ConstInt(norm(truncd as i64, *w), *w));
```
**Severity**: MAJOR.
**Why wrong**: `i64::MAX = 9223372036854775807`. Cast to f64, it rounds to **9223372036854775808.0** = 2^63, because f64 has only 53 bits of mantissa. That means:
- `truncd = 9223372036854775808.0` passes `truncd > hi` (false — they're equal).
- `truncd as i64` in Rust uses saturating conversion on nightly/modern stable, producing `i64::MAX`. But semantically 2^63 is **one past** i64's range.
- Similarly, values in `(i64::MAX, 2^63]` will appear to pass the range check.

The fold silently produces `i64::MAX` for values outside the true i64 range — a wrong answer. At runtime, AArch64 `FCVTZS` on a value >= 2^63 saturates to `i64::MAX`. Rust's `as` saturates too. So... by coincidence this **matches hardware**. But the logic is wrong: the range check should use strict inequality on an exclusive hi, `truncd >= 2^63` should bail.

More importantly, `i8::MAX = 127` casts exactly to 127.0, and `i32::MAX = 2147483647` casts exactly to 2147483647.0 — but `127.5.trunc() = 127.0` passes `truncd > hi` (false), and `127.0 as i8 = 127`. Fine. But `127.9.trunc() = 127.0`, still fine. This is only a correctness issue for i64 near the boundary.

**Repro**:
```fortran
real(8) :: r = 9.223372036854776e18  ! rounds to 2^63 in f64
integer(8) :: i
i = int(r)  ! Fortran INT() toward zero
```
Expected per standard: undefined/implementation-defined (value out of integer range). Hardware: saturates to i64::MAX. Our const-fold: silently emits `i64::MAX`. Technically matches hardware, but the bounds check is broken and could allow other out-of-range folds once someone touches it.

**Fix**: use exclusive upper bound: `truncd >= (i64::MAX as f64) + 1.0` → also 2^63, so check `truncd >= 9223372036854775808.0`. Better: test `!truncd.is_finite() || truncd < lo || truncd >= hi_plus_one` where `hi_plus_one = 2^(bits-1)` as f64. For i8/i16/i32 use `(i8::MAX as i64 + 1) as f64` etc.

### M-B. `const_fold::Shl` with shift count ≥ width emits 0, but **AArch64 SHL masks** the shift count — producing a **non-zero** result
**File**: `src/opt/const_fold.rs:212-228`
```rust
if (0..bits).contains(&bv) {
    return Some(InstKind::ConstInt(norm(av.wrapping_shl(bv as u32), *w), *w));
}
// Shift count >= width is implementation-defined
// in C; AArch64 returns 0. Match that.
return Some(InstKind::ConstInt(0, *w));
```
**Severity**: MAJOR.
**Why wrong**: The comment is **incorrect**. AArch64 `LSL Xd, Xn, Xm` uses `Xm & 0x3F` (for 64-bit) or `Xm & 0x1F` (for 32-bit) as the actual shift count. A shift by exactly `bits` wraps to 0, producing `av` (identity), not 0. A shift by `bits+1` produces `av << 1`. See ARMv8 ARM, UBFM/LSLV definitions.

So `shl x, 32` on an i32 produces `x`, not `0`. Our folder emits `0`. At `-O2`, the optimized constant and the runtime-computed value will disagree for any Fortran code that reaches a constant shift at or past the width. This is also aggravated by the ISHFT lowering on `src/ir/lower.rs:671`, which computes both the left and the right branch and selects. The left branch is `shl(args[0], args[1])` — if `args[1]` is a statically known negative number, const_fold will see `bv = -N` (sign-extended), `(0..bits).contains(&-N) = false`, and emit `0`. The Select then returns `0` when it should have returned the right-shifted value. And on AArch64, even the runtime would produce a different answer (it masks to low 5/6 bits of the negative number, which is nonzero).

**Repro** (as IR):
```
%v = const_int 1 : i32
%n = const_int 32 : i32
%s = shl %v, %n : i32
; ConstFold produces ConstInt(0, I32)
; Runtime on AArch64 produces 1 (identity — mask of 32 & 31 = 0)
```
And with the ISHFT path — `ishft(1_i32, 33)` — the Shl branch gets evaluated as `shl 1, 33`, folder emits 0, but AArch64 emits `1 << (33 & 31) = 1 << 1 = 2`. Mismatch.

Similar bugs in LShr (line 229-242, same `return 0`) and AShr — AShr does the right thing by replicating the sign bit, which **also disagrees with AArch64** (which would emit `av >> (count & 31)`).

**Fix**: either bail (return None) for out-of-range counts, or mask the count to `bits-1` and re-enter the in-range path. Matching AArch64 means `bv & (bits-1)`.

### M-C. `const_fold::Shl` treats negative shift counts as "out of range" and emits 0
**File**: `src/opt/const_fold.rs:212-228`
**Severity**: MAJOR.
**Why wrong**: `bv as i64` stays signed. `(0..bits).contains(&bv)` with `bv = -1` is false. Folder hits the `return Some(InstKind::ConstInt(0, *w))` branch. But `av.wrapping_shl(-1 as u32)` = `av.wrapping_shl(0xFFFFFFFF)` which Rust defines as `av.wrapping_shl(0xFFFFFFFF % 32) = av.wrapping_shl(31)`. So the runtime-semantic answer would be `av << 31`, not 0.

More importantly: Fortran's ISHFT(a, -1) is a right shift by 1. The lowerer handles this by computing **both** the Shl(a, -1) and the LShr(a, 1) branches and selecting between them. When the const_fold sees Shl(a, -1) with a constant -1, it folds to 0. When the const_fold also sees the Select's condition as constant-false (because `-1 >= 0` folds to false), the Select picks the LShr branch — so the end result is correct! But the Shl(a, -1) instruction, before the Select fold removes it, has been folded to const(0), which is **dead-but-wrong**. Not immediately observable, but CSE or downstream passes could key off of it in surprising ways.

**Fix**: for negative `bv`, return None (leave it alone — runtime semantics are implementation-defined).

### M-F. `const_fold::FloatToInt` uses f64 `truncd` against f64 bounds even when the source was f32
**File**: `src/opt/const_fold.rs:298-317`
**Severity**: MAJOR.

### Med-6. `licm::is_hoist_candidate` hoists `Select` instructions — but a Select's condition is a loop-invariant **guard** that may prevent a poison/trap in one arm
**File**: `src/opt/licm.rs:54-65`
**Severity**: MEDIUM.
**Why wrong**: `Select` is currently on the hoistable list (not in the exclusion list). A Select whose condition is invariant and whose arms are invariant is safe to hoist — the classic `cond ? x : y` where all three are loop-constant. But consider:
```
; inside loop, after bounds check against i
%bad = idiv %a, %b_maybe_zero  ; loop-invariant values
%good = const 0
%cond = icmp ne %b_maybe_zero, 0
%r = select %cond, %bad, %good  ; selects 0 when div-by-zero
```
The `select` itself is pure and all operands are loop-invariant. LICM would hoist `%bad` (the div) out of the loop too, because div is... wait, Div isn't currently in the hoist exclusion list either. **That's the real bug**: IDiv and IMod are candidates for LICM, and hoisting them out of a guarding conditional turns guaranteed-no-op cases into trap/UB cases.

**Repro**:
```fortran
do i = 1, 10
  if (b /= 0) then
    c = a / b
    call use(c)
  end if
end do
```
If `a`, `b`, `c` live in allocas, loads block everything and LICM does nothing. But if the lowerer ever registerizes these, the invariant `a/b` gets hoisted out of the `if`, causing SIGFPE when `b == 0`. Fortran's semantics say `a/b` only executes when the guard is true. LICM would break that.

**Fix**: exclude trap-prone pure operations (`IDiv`, `IMod`, `FDiv`, `FSqrt`, `FPow`) from `is_hoist_candidate`, or require a proof that the operand that could trap is non-trapping. LLVM has the concept of "safe to speculate" for exactly this reason.

## Surprises (things that LOOK wrong but actually work)

### S-1. `const_fold::IDiv/IMod` `i64::MIN / -1` check appears not to cover narrow widths, but `norm()` correctly wraps
The guard at line 112 (`if av == i64::MIN && bv == -1 { return None; }`) only protects against Rust panicking on true 64-bit overflow. For narrower widths, the Rust `/` operation succeeds (e.g., `-128_i64 / -1_i64 = 128_i64`, no panic), then `norm()` truncates and re-sign-extends to yield the correct `-128` two's-complement wraparound. I worked through i8 and i32 cases and both match AArch64 SDIV semantics. **Not a bug.**

### S-2. `const_fold::try_fold` walks function linearly without respecting RPO
A single const_fold pass visits blocks in `func.blocks.iter()` order. For non-RPO layouts, an instruction in block `B[k]` might reference a constant defined in `B[k+1]` (if `B[k+1]` dominates `B[k]` but appears later in the vector). In that case, the first pass would miss the fold. **But** the pass manager runs to fixpoint, so a second pass picks it up. Audit test `audit_const_fold_non_rpo_block_order` covers this. **Not a bug.**

### S-3. `licm::find_natural_loops` produces one `NaturalLoop` per header, merging multiple back-edges naturally
The `by_header` grouping on line 274 collapses all back-edges into the same header into one `NaturalLoop` with multiple latches. The body union is computed via the shared header (line 283-298), which is correct for reducible loops. **Not a bug**, though it couples loosely with the self-loop bug you already found (M-7) — the latch==header edge still produces a 1-element latches vector, the body-computation walk starts from the latch (which is the header), adds header to body already, then immediately stops because `p == header` (continue). Self-loops with no other back path produce body={header}, then `find_preheader` sees all header predecessors as out-of-loop... which is exactly the M-7 bug you documented. So S-3 is correct for multi-latch loops; the self-loop degenerate case is M-7.

## New adversarial test suggestions (haven't written these — describing for you to verify)

1. **C-C reproducer**: Select whose chosen arm is a ConstFloat with width F32 but whose declared type is F64. After const-fold, check that the rewritten ConstFloat has width F64.

2. **M-A reproducer**: FloatToInt from f64 near 2^63 boundary. Specifically, fold `FloatToInt(2^63_as_f64, I64)` — should return None (or a sentinel) since 2^63 is out of range.

3. **M-B reproducer**: `shl 1_i32, 32_i32` — assert fold produces `1` (matching AArch64 identity wrap) or bails to leave the Shl in place, but **not** `ConstInt(0, I32)`.

4. **M-C reproducer**: `shl 1_i32, (-1)_i32` — same expectation: either produce the masked-count result or bail.

5. **Med-6 reproducer**: build a synthetic loop with a guarded `idiv x, y` where y is loop-invariant. Run LICM. Assert the idiv is **not** hoisted out of the guarding block.

6. **IR shape for C-B / Min-2**: nested loops where an inner loop's preheader is inside an outer loop's body. Build the IR manually, run LICM, and check that all hoisted instructions land in valid dominating positions.
